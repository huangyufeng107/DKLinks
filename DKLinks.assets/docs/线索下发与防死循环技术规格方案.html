本规格书用于指导 D客连 系统从“陪跑影子模式”平稳演进至“试点供应商直连网关模式”。明确规定试点供应商直采接入、D客连规则闭环裁决、带标下发线索中心、防死循环环路阻断以及后链路更新反哺的全套数据流与接口协议。

评审状态：已通过 模式：前置治理网关 (BFF Filter) 核心机制：双向打标 + 幂等去重 责任人：D客连架构组 & 线索中心团队
1. 业务背景与方案演进 架构演进

1.1 两个阶段的核心差异与职责边界

流转维度 阶段一：陪跑观察期（当前线上状态） 阶段二：试点供应商直连期（本次目标）
入口链路 供应商 ➔ 车巴巴 ➔ 线索中心 试点新供应商 ➔ D客连 OpenAPI；其余老供应商仍走车巴巴
D客连定位 旁路影子系统 (Shadow)：被动接收线索中心镜像，观察校验功能 前置网关中枢 (Gateway & Filter)：闭环处理清洗、黑名单拦截、排期扣费、意向映射
下发决策权 线索中心拥有全量决定权 D客连前置裁决：命中规则直接本地阻断；合格线索才推送线索中心
核心下发通道 线索中心 ➔ COC / NEV中台系统 保持不变：线索中心 ➔ COC / NEV中台系统（保障主机厂下游稳定）
后链路数据流 COC ➔ 线索中心 ➔ 镜像同步 D客连 COC ➔ 线索中心 ➔ 根据 dk_lead_id 更新 D客连对应线索
💡
架构师设计原则说明： 我们没有让 D客连 直接替代线索中心去对接 COC/NEV 中台，而是让 D客连 作为“前置准入网关”，把治理合格的线索委托线索中心统一下发。这种模式对下游核心交易系统完全透明零改造，极大降低了灰度切换的技术与业务风险。
2. 核心流转时序图说明 Mermaid / 矢量交互
完整展示：①供应商直推 ➔ ②D客连前置裁决 ➔ ③准入通过打标推线索中心 ➔ ④线索中心阻断反向同步 ➔ ⑤后链路状态反哺更新。
阶段一回顾：全量线索由车巴巴流向线索中心，D客连仅作为下游镜像系统同步观察，两端独立跑批比对。
3. 防死循环三道防线体系 (Defense in Depth) 核心风控

为什么会产生死循环？若 D客连 推送准入线索给线索中心后，线索中心将其当成“全新产生线索”广播给订阅方（包含了 D客连），D客连收到后若再次触发规则并调用下发，就会形成 A ➔ B ➔ A ➔ B 的无限雪崩。为保证绝对安全，我们构建了三道互为补充的防线：

🛡️ 第 1 道防线 线索中心出向
来源标识阻断 (Source Filter)
D客连推线索时携带 source_system='DKLINKS'。线索中心在调用同步任务时增加前置拦截：if ("DKLINKS".equals(source)) return; 根本不发射广播。
🛡️ 第 2 道防线 架构解耦
事件主题隔离 (Topic Split)
将消息彻底拆分为两个 Topic：
• LEAD_CREATED（仅老渠道触发）
• LEAD_STATUS_UPDATE（全渠道状态回传）
D客连仅订阅状态更新 Topic。
🛡️ 第 3 道防线 D客连入口兜底
全局幂等防御 (Idempotency)
即使线索中心因运维失误把线索重新推来，D客连入库时检测到 source_lead_id 或 dk_lead_id 已存在，直接静默丢弃，绝不二次执行下发。

6. 核心业务处理伪代码 (Pseudo-code) 实现指导

6.1 D客连端：前置治理裁决与下发调用

Python / Go 伪代码
def handle_supplier_incoming_lead(request_payload):
    # 1. 签名认证
    verify_signature(request_payload)

    # 2. 幂等排重 (防供应商重复回调)
    if clue_repo.exists(request_payload.source_channel, request_payload.source_lead_id):
        return {"code": 0, "message": "Duplicate ignored", "data": {"status": "ACCEPTED"}}

    # 3. 实例化线索，生成本地业务ID dk_lead_id
    lead = ClueLead(
        dk_lead_id = id_gen.next_id(),
        origin_source_type = 2, # 直连试点
        source_channel = request_payload.source_channel,
        source_lead_id = request_payload.source_lead_id,
        phone = request_payload.customer_phone
    )

    # 4. 执行规则引擎
    rule_res = RuleEngine.evaluate(lead)
    if rule_res.is_blocked:
        lead.dispatch_status = 2 # 拦截
        lead.intercept_rule_code = rule_res.rule_code
        clue_repo.save(lead)
        return {"code": 0, "message": "Accepted", "data": {"status": "BLOCKED"}}

    # 5. 准入通过：匹配排期扣减预算、转换意向等级
    lead.smartcode = ScheduleService.match_smartcode(lead)
    lead.lead_level = IntentService.map_level(request_payload)
    lead.dispatch_status = 0
    clue_repo.save(lead)

    # 6. 调用线索中心 (带关键标识)
    push_body = FieldMapper.transform(lead)
    push_body["source_system"] = "DKLINKS"
    push_body["dk_lead_id"] = lead.dk_lead_id

    resp = LeadCenterClient.push_lead(push_body)
    if resp.code == 0:
        lead.dispatch_status = 1 # 成功下发
        lead.center_lead_id = resp.data.center_lead_id
        lead.dispatch_time = now()
    else:
        lead.dispatch_status = 3 # 失败入补偿重试队列
        retry_queue.push(lead.dk_lead_id)

    clue_repo.save(lead)
    return {"code": 0, "message": "Success", "data": {"status": "ACCEPTED"}}

6.2 线索中心端：出向阻断与防死循环逻辑 (核心关键)

Java / Spring Boot 伪代码
@PostMapping("/push-from-dklinks")
public ApiResponse handleLeadFromDkLinks(@RequestBody LeadDTO dto) {
    // 1. 入库线索中心并下发 COC/NEV 中台
    LcLead lead = leadCenterService.saveAndDispatchToCoc(dto);

    // 2. 【核心防死循环判断】
    if ("DKLINKS".equalsIgnoreCase(dto.getSourceSystem())) {
        // 来自 D客连 准入的线索，绝对不向 D客连 发送新线索生成事件！
        log.info("Lead {} is from DKLINKS, skip reverse sync to avoid dead loop.", lead.getId());
        return ApiResponse.success(new LeadCenterResult(lead.getId()));
    }

    // 3. 其余非 D客连 来源线索 (如老渠道车巴巴)，正常广播给 D客连 陪跑观察
    mqProducer.send("TOPIC_LEAD_CREATED", lead);

    return ApiResponse.success(new LeadCenterResult(lead.getId()));
}
